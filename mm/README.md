依頼された戦略を、**Hummingbot で動く形**・**手元で検算できる形**の両方にしたもの。

```
mm/core.py                        戦略の本体（外部依存なし。これが正本）
mm/tape.py                        約定テープ（合成／手元CSV読み込み）

mm/hummingbot/last_trade_mm_core.py  core.py と同一（scripts/sync_hummingbot.py で同期）
```

## 検証でわかったこと（4つ）

シミュレータを回して出てきたもの。**どれも設計に直結します。**

### 1. 「直近約定価格 ＝ 今の適正価格」は、構造的にズレている

直近の約定価格は、正確には

```
直近約定価格 ＝ 中値 ± 板の片側幅（最後に取りに来た側の符号）
```

です。買いが入った直後は中値より高く、売りが入った直後は中値より低い。
**その値を中心に気配を置くと、直前に動いた側へ毎回寄せて置くことになります。**
買いが入ったら自分も高く買いに行き、売りが入ったら安く売りに行く。追いかけて
いるだけで、鞘になりません。

直し方は簡単で、**直近の買い約定と売り約定の中点**を適正価格に使います。

| 適正価格の取り方 | 1往復あたりの粗利 |
| --- | --- |
| 直近約定そのまま | −1.08 bps |
| 中点（偏り除去） | −0.24 bps |

（板の片側幅 1bps・自分も 1bps・レンジ相場。`debias_last_trade` で切り替え）

副産物として、この中点から**板の片側幅そのものが推定できます**
（`LastTradeMarketMaker.market_half_spread_bps`）。スプレッドの下限を決めるのに使えます。

### 2. 在庫上限が、この戦略で一番効いている

70%上昇するトレンドのテープで、在庫上限のあるなしを比べた結果です。

| | 損益 | 最大在庫 | 最終在庫 |
| --- | --- | --- | --- |
| 在庫上限あり（本戦略） | **−82.7** | 0.0045 | −0.0018 |
| 在庫上限なし（Simple PMM 相当） | **−7,973.2** | **0.205** | −0.205 |

**損失が約96分の1。** 上限が無いと、上げ続ける相場にアスクを取られ続けて、
注文サイズの205倍のショートを抱えて終わります。依頼文にあった
「買いばかり約定してポジションが片側に偏る」の、逆方向版そのものです。

- 上げ相場 → アスクを取られ続ける → **ショートに偏る**
- 下げ相場 → ビッドを叩かれ続ける → **ロングに偏る**

在庫スキュー（偏った側に価格を寄せる）も効いていて、上限に触る前に在庫を
戻します。実際、既定のスキューだと上限まで到達しないことのほうが多いです。

### 3. 「新しい約定が出るたびに出し直す」は、そのままだと手数料負けする

依頼文のとおり毎約定で出し直すと、板を触る回数だけが増えます。

急変ありのテープ（片側3bps・maker 2bps）:

| 出し直ししきい値 | 出し直し回数 | 手数料 | 損益 |
| --- | --- | --- | --- |
| 0.5 bps | 11,793 | 55.6 | −84.0 |
| 2 bps | 5,560 | 51.7 | −79.3 |
| 8 bps | 1,149 | 27.8 | −51.9 |
| 12 bps | 629 | 17.4 | **−39.1** |

**しきい値は片側スプレッドと同じかそれ以上**にしてください。既定を 8bps に
しました。小さくしても粗利は増えず、手数料と約定回数だけが増えます。

### 4. 成立条件は、手数料とボラで決まってしまう

1往復あたりの粗利は、板の片側幅 S と1約定あたりの中値ボラ V で、ほぼ

```
粗利(bps) ≒ 2S − 3.8V
```

になります（実測、`run_sim.py sweep`）。

```
              V=0.1     V=0.25      V=0.5      V=1.0      V=2.0
S=0.5          0.62       0.05      -0.90      -2.79      -6.47
S=1.0          1.62       1.04       0.09      -1.79      -5.49
S=2.0          3.62       3.04       2.08       0.18      -3.52
S=4.0          7.62       7.04       6.07       4.16       0.40
S=8.0         15.62      15.02      14.04      12.09       8.30
```

ここから、**成立の必要条件**は

```
2S − 3.8V  >  往復 maker 手数料
```

参考値（自分の口座で必ず確認してください）:

| | 片道 maker | 往復 | 必要な 2S−3.8V |
| --- | --- | --- | --- |
| spot VIP0 | 約 10 bps | 約 20 bps | 20 超 |
| perp VIP0 | 約 2 bps | 約 4 bps | 4 超 |
| maker リベートあり | 負 | 負 | 0 でも可 |

**BTC-USDT は板の片側幅が 0.5〜1bps しかないので、2S は 1〜2bps。** perp の
往復 4bps にすら届きません。つまり **BTC でこの戦略を回すと、手数料で構造的に
負けます。** シミュレータでも全ての地合いで「不成立」と出ました。

候補になるのは次のどれかです。

1. **板の広い銘柄**（流動性の薄いアルト。S が 10〜50bps ある）
2. **maker リベートのある取引所**（手数料が負になれば粗利 0 でも残る）
3. **VIP 階層を上げる**

`enforce_fee_floor`（既定 ON）は、往復手数料を割るスプレッドでは発注しない
安全装置です。これを ON にしたまま一度も発注されないなら、その銘柄では
**そもそも成立していない**ということです。

### シミュレータの弱点（必ず読んでください）

**「自分がその価格で板の先頭にいた」前提**で約定させています。実際には同じ
価格に先客が並ぶので、**ここで出る約定回数と利益はどちらも上振れします。**
つまり出てくる数字は上限であって、期待値ではありません。

それでも上の4つの結論は向きが変わりません。約定が上振れしているということは、
**手数料も上振れ**しており、かつ粗利が足りないという結論は**より厳しくなる**
方向だからです。

実際の数字は Hummingbot のペーパートレード（依頼の手順4）で取ってください。
`run_sim.py csv` に手元で落とした約定履歴を食わせれば、同じ指標で比較できます。
